# 03. 날짜와 시간 — epoch · 타임존 · java.time · DB · cron

> `/timestamp` `/cron` 을 만들면서 정리한 것.
> 시간은 "그냥 숫자"처럼 보여서 방심하는데, 실무 버그가 가장 조용히 오래 살아남는 영역이다.
> 값은 전부 실제로 돌려 확인했다.

---

## 0. 한 장 요약

| 규칙 | 이유 |
|---|---|
| **저장·전송은 UTC, 표시만 로컬** | 서버가 어디 있든 같은 값. 서머타임에도 안 흔들린다 |
| **`LocalDateTime` 은 시각이 아니다** | 타임존이 없다. "벽시계에 적힌 글자"일 뿐 |
| **오프셋 ≠ 타임존** | `+09:00` 은 한 순간의 값, `Asia/Seoul` 은 규칙의 집합 |
| **10자리는 초, 13자리는 밀리초** | 이걸 헷갈리면 1970년이나 5만년 뒤가 나온다 |
| **cron 은 5필드가 표준, Spring 은 6필드** | 맨 앞에 **초**가 붙는다 |

## 1. epoch — 시간을 숫자 하나로

**Unix epoch** = 1970-01-01 00:00:00 **UTC** 부터 흐른 초.

```
0             → 1970-01-01T00:00:00Z
1786968404    → 2026-08-17 (10자리 = 초)
1786968404472 → 같은 시각    (13자리 = 밀리초)
```

**자릿수로 단위를 구분한다** — 지금 시각 기준 초는 10자리, 밀리초는 13자리다.
`/timestamp` 도구가 자동 판별하는 근거가 이거다. 헷갈리면 1970년 근처나 먼 미래가 나온다.

### 2038년 문제

32비트 부호 있는 정수의 최대값 `2147483647` 초는 **2038-01-19T03:14:07Z** 다.
그 다음 초에 음수로 넘어가 1901년이 된다.

- Java `long`, JS `number` 는 문제없다
- **MySQL `TIMESTAMP` 는 아직 이 한계를 가진다**(`1970-01-01` ~ `2038-01-19`).
  만료일·계약 종료일처럼 2038년을 넘을 수 있는 값에는 `DATETIME` 을 쓴다
- 임베디드·구형 C 시스템은 여전히 위험하다

### JS 의 함정 하나

```js
Date.now()          // 1786968404472  (밀리초)
```

JS 만 밀리초 기준이다. Java `Instant.getEpochSecond()`, Python `time.time()`, Go, DB 함수는
대부분 초다. **API 경계에서 단위를 반드시 명시한다** — 필드명을 `expiresAt` 말고
`expiresAtMs` / `expiresAtSec` 로 두면 사고가 준다.

> JWT 의 `exp` `iat` `nbf` 는 **초**다(RFC 7519). JS 에서 `Date.now()` 를 그대로 넣으면
> 1000배 미래가 되어 만료 검사가 무력해진다. [06_암호와_JWT.md](06_암호와_JWT.md) §6.4 참조.

## 2. 오프셋과 타임존은 다른 것이다

| | 예 | 뜻 |
|---|---|---|
| **오프셋** | `+09:00` | UTC 와의 차이. **한 순간의 사실** |
| **타임존** | `Asia/Seoul` | "언제 오프셋이 얼마인가"의 **규칙 전체**. 서머타임 이력을 포함 |

서울은 오프셋이 늘 `+09:00` 이라 차이를 못 느끼지만, 뉴욕은 `America/New_York` 하나가
겨울 `-05:00` · 여름 `-04:00` 두 오프셋을 오간다.

**미래 시각을 다룰 때 이 차이가 실제 버그가 된다.**
"2027년 3월 15일 오전 9시(뉴욕)에 알림" 을 오프셋으로 저장해 두면,
그 사이 서머타임 규칙이 바뀔 경우 1시간 어긋난다. 그래서 **미래 약속은 타임존 ID 로 저장**한다.

> 한국도 1948~1988년 사이 몇 차례 서머타임과 UTC+8:30 시기가 있었다.
> `Asia/Seoul` 은 그 이력을 다 갖고 있다. 그래서 옛 날짜를 다룰 때 `+09:00` 고정은 틀릴 수 있다.

### tzdata

타임존 규칙은 각국 정부가 바꾼다(2023년에도 여러 건). 그 데이터베이스가 **tzdata** 이고
JDK·OS·DB 가 각자 들고 있다. **JDK 를 오래 안 올리면 타임존 규칙이 낡는다.**

## 3. Java 의 시간 API — 무엇을 언제

`java.util.Date` `Calendar` `SimpleDateFormat` 은 **쓰지 않는다.**
가변이고 스레드 안전하지 않으며(운영에서 `SimpleDateFormat` 을 static 으로 공유하면 값이 깨진다),
월이 0부터 시작하는 등 설계가 낡았다. Java 8 의 `java.time` 을 쓴다.

| 타입 | 갖고 있는 것 | 언제 쓰나 |
|---|---|---|
| **`Instant`** | epoch 기준 한 순간 | **DB 저장·API 전송·로그**. 기본값으로 삼는다 |
| `LocalDate` | 날짜만 | 생일, 기념일 |
| `LocalTime` | 시각만 | 영업 시작 09:00 |
| **`LocalDateTime`** | 날짜+시각, **타임존 없음** | ⚠️ 아래 설명 |
| `OffsetDateTime` | 날짜+시각+오프셋 | 외부 API 주고받기 |
| **`ZonedDateTime`** | 날짜+시각+타임존 규칙 | **사용자에게 보여줄 때**, 미래 약속 |
| `Duration` | 시간 기반 간격(초·나노) | 두 `Instant` 사이 |
| `Period` | 날짜 기반 간격(년·월·일) | 나이, 개월 수 |

### `LocalDateTime` 이 위험한 이유

```java
LocalDateTime.now()   // "2026-08-17T21:00" — 이게 어느 지역 9시인지 정보가 없다
```

**시각이 아니라 벽시계에 적힌 글자**다. 그걸 그대로 DB 에 넣고 서버 타임존이 바뀌면
값의 의미가 통째로 달라진다. 로컬(KST)에서 개발하고 운영 서버가 UTC 면 9시간이 어긋난다.

```java
// ✅ 저장: 순간을 저장한다
Instant now = Instant.now();

// ✅ 표시: 그 순간을 사용자 지역으로 변환한다
ZonedDateTime seoul = now.atZone(ZoneId.of("Asia/Seoul"));

// ⚠️ 서버 기본 타임존에 의존한다 — 로컬과 운영이 다르면 결과가 달라진다
LocalDateTime.now();
ZoneId.systemDefault();
```

> **운영 서버 타임존은 UTC 로 두는 게 안전하다.** 그러면 로그·DB·계산이 전부 한 기준이고,
> 지역 변환은 표시 직전에만 일어난다.
> Spring Boot 에서 JDBC 시간 처리를 못 박으려면 `spring.jpa.properties.hibernate.jdbc.time_zone: UTC`.

### `Duration` vs `Period`

```java
Duration.between(i1, i2).toHours();      // 정확한 시간 차 (서머타임 무시하고 실제 흐른 시간)
Period.between(d1, d2).getYears();       // 달력상 차이 (나이 계산은 이쪽)
```

"한 달 뒤"는 `Duration.ofDays(30)` 이 아니라 `plusMonths(1)` 이다.
1월 31일 + 1개월은 2월 28일로 **잘려서** 처리된다(2월 31일이 없으니까).

## 4. DB 의 시각 타입

| DB · 타입 | 저장 방식 | 주의 |
|---|---|---|
| MySQL `DATETIME` | **적은 값 그대로**. 타임존 개념 없음 | 범위 1000~9999년. 어느 지역 시각인지 앱이 알아야 함 |
| MySQL `TIMESTAMP` | UTC 로 변환해 저장, 조회 시 **세션 타임존**으로 변환 | **2038년 한계**. 세션 타임존에 따라 값이 달라 보인다 |
| PostgreSQL `timestamp` | 그대로 저장(타임존 없음) | MySQL `DATETIME` 과 비슷 |
| PostgreSQL **`timestamptz`** | UTC 로 저장, 조회 시 세션 타임존으로 변환 | **권장**. 8바이트, 2038 문제 없음 |

**`timestamptz` 는 이름이 오해를 부른다** — 타임존을 *저장하지 않는다*.
UTC 로 정규화해 저장하고 보여줄 때만 변환한다. 원래 어느 타임존이었는지가 필요하면
타임존 ID 컬럼을 따로 둔다.

```sql
-- MySQL: 세션 타임존에 따라 TIMESTAMP 조회 결과가 달라진다
SET time_zone = '+00:00';
SELECT created_at FROM t;   -- 2026-08-17 03:00:00
SET time_zone = '+09:00';
SELECT created_at FROM t;   -- 2026-08-17 12:00:00   같은 행인데!
```

로컬과 운영의 세션 타임존이 다르면 "데이터가 이상하다"는 신고가 여기서 나온다.

## 5. ISO 8601 / RFC 3339 — 문자열로 주고받기

```
2026-08-17T12:00:00+09:00     오프셋 명시  ← API 에서 이걸 쓴다
2026-08-17T03:00:00Z          Z = UTC (Zulu). 위와 같은 순간
2026-08-17T12:00:00           오프셋 없음 — 어느 지역인지 모른다. 쓰지 않는다
2026-08-17                    날짜만
P1Y2M3D / PT1H30M             기간(Period/Duration) 표기
```

**규칙**: API 로 시각을 주고받을 때는 **항상 오프셋이나 Z 를 붙인다.**
오프셋 없는 문자열은 받는 쪽이 자기 타임존으로 해석해 버린다.

> `2026-08-17 12:00:00`(가운데가 공백)은 ISO 8601 이 아니다. `T` 를 넣는다.
> JS `new Date("2026-08-17")` 는 **UTC 자정**으로, `new Date("2026-08-17T00:00:00")` 는
> **로컬 자정**으로 해석한다 — 이 차이로 하루가 밀리는 버그가 흔하다.

## 6. cron 표현식

`/cron` 도구가 다루는 것. **필드 수가 구현마다 다르다**는 게 첫 함정이다.

```
표준 Unix (5필드)
┌ 분(0-59)
│ ┌ 시(0-23)
│ │ ┌ 일(1-31)
│ │ │ ┌ 월(1-12)
│ │ │ │ ┌ 요일(0-7, 0과 7 모두 일요일)
* * * * *

Spring / Quartz (6필드) — 맨 앞에 초가 붙는다
초 분 시 일 월 요일
0  0 3 * *  *        매일 새벽 3시 정각
```

**Spring 의 `@Scheduled(cron = "0 0 3 * * *")` 를 5필드로 쓰면 예외가 난다.**
반대로 crontab 에 6필드를 넣으면 의미가 통째로 밀린다.

| 기호 | 뜻 | 예 |
|---|---|---|
| `*` | 모든 값 | |
| `,` | 나열 | `1,15` = 1일과 15일 |
| `-` | 범위 | `9-18` = 9시부터 18시 |
| `/` | 간격 | `*/10` = 10분마다, `0/15` = 0분부터 15분마다 |
| `?` | 지정 안 함 (Quartz, 일/요일 중 하나에) | |
| `L` | 마지막 (Quartz) | `L` = 말일 |

```
0 0 9 * * MON-FRI      평일 오전 9시 (Spring)
0 */30 * * * *         30분마다
0 0 0 1 * *            매월 1일 자정
```

### 실무에서 조심할 것

- **일(day-of-month)과 요일(day-of-week)을 동시에 지정하면 OR 다** — 둘 다 만족이 아니라 둘 중 하나.
  `0 0 1 * MON` 은 "1일 **또는** 월요일"이다
- **타임존**: `@Scheduled(cron = "...", zone = "Asia/Seoul")` 로 명시한다.
  안 하면 서버 기본 타임존을 따라가서 UTC 서버에서 9시간 어긋난다
- **서머타임이 있는 지역에서 새벽 2~3시 작업은 건너뛰거나 두 번 돈다.**
  중요한 배치는 그 시간대를 피한다
- **인스턴스가 여러 대면 같은 작업이 여러 번 돈다.** 분산 락(Redis, DB)이나
  ShedLock 같은 걸 쓴다

## 7. 자주 틀리는 날짜 계산

### 윤년

```
4로 나누어떨어지면 윤년, 단 100으로 나누어떨어지면 평년, 단 400으로 나누어떨어지면 윤년
1900 → 평년   2000 → 윤년   2024 → 윤년   2100 → 평년
```

`year % 4 === 0` 만 쓴 코드는 2100년에 틀린다. `Year.isLeap(y)` 를 쓴다.

### 나이

한국식 "만 나이"는 생일이 지났는지를 봐야 한다. 직접 계산하지 말고,

```java
Period.between(birthDate, LocalDate.now()).getYears();
```

### 두 날짜 사이 일수

```java
ChronoUnit.DAYS.between(d1, d2);   // 끝 날짜 제외 (반열린 구간)
```

"8/1 ~ 8/3 은 며칠?" 이 2일인지 3일인지는 **요구사항에 달렸다**.
근무일 계산이면 보통 양 끝을 포함해 3일이다. 날짜 도구를 만들 때 포함/제외를
고르게 해 둔 이유다.

### 월 말일

```java
LocalDate.of(2026, 1, 31).plusMonths(1);   // 2026-02-28 (잘린다)
```

이게 "1월 31일에 가입한 사람의 다음 결제일" 문제다. 잘린 뒤 다시 `plusMonths(1)` 를 하면
3월 28일이 되어 원래 31일로 못 돌아온다. **기준일을 따로 보관**하고 매번 그 기준에서 계산한다.

### 윤초

UTC 에는 가끔 23:59:60 이 있다(1972년 이후 27회). Unix epoch 는 윤초를 세지 않고
그 순간을 되풀이하거나 뭉갠다("leap smear"). 금융 거래 로그처럼 초 단위 순서가 중요한 게 아니면
신경 쓸 일은 거의 없다.

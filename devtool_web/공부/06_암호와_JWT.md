# 06. 해시와 JWT

교과서가 아니라 **직접 만져 보고 이해한 대로** 적은 메모다.
`/jwt` 와 `/hash` 를 쓰다가 막히는 두 지점만 다룬다 — **JWT 의 비밀키가 뭔지**, 그리고 **해시에 왜 키가 필요한지**.

---

## 1. JWT — 비밀키가 어떻게 오가나

### 전체 흐름

```
① 32byte 숫자
      │  base64 인코드
      ▼
② 32byte 를 인코딩한 문자     ← 개발자가 입력하는 값
      │
      ▼
③ 서버 yml 에 secret key 로 적어 둠
      │  base64 디코드
      ▼
④ 원래 32byte 숫자를 얻어 서버가 들고 있음
```

여기서부터는 서버와 클라이언트가 주고받는다.

| 시점 | 서버 | 클라이언트 |
|---|---|---|
| 로그인 | **원래 32byte** 로 토큰 발급 | 받은 토큰 저장 |
| 요청 | **원래 32byte** 로 토큰 검증 | 요청에 토큰 포함 |

**서명도 검증도 ④의 32byte 로 한다.** yml 에 적힌 문자열 자체가 키가 아니다.

### 참고 1 — 아무 문자열이나 쓰면 안 되는 이유

문제는 **아무 문자열이나 적으면 디코딩이 될지, 되더라도 32byte 가 될지 모른다**는 것이다.

그래서 이런 명령을 쓴다.

```bash
openssl rand -base64 32
# XBJxvOjybQbZLKimwxG5zo0BZIywlAZ0y8mNmvBB7n4=
```

- **44문자**가 나온다
- 이 44문자는 **32byte 로 디코딩되는 것이 보장된 인코딩 문자**다

### 참고 2 — yml 에 적는 값은 인코딩된 문자열

정석은 이렇다.

- 개발자가 서버 yml 에 쓰는 값 = **인코딩된 문자열**(위의 44문자)
- 서버는 이 값을 **디코딩한 뒤** 발급·검증에 쓴다

### 이 사이트의 `/jwt` 에서 "키 해석" 을 고르는 이유

`/jwt` 는 비밀키를 **글자 그대로** 볼지 **Base64 디코드**해서 볼지 고르게 한다.
같은 문자열이라도 해석이 다르면 키 바이트가 달라지고, 그러면 서명도 달라지기 때문이다.

| 해석 | 자바 코드 |
|---|---|
| Base64 디코드 | `Decoders.BASE64.decode(secret)` |
| 글자 그대로 (UTF-8 바이트) | `secret.getBytes(UTF_8)` |

**본인이 쓰는 프로젝트에 맞춰 고르면 된다.**

> 예: 내 프로젝트에서 JWT 검증을 Base64 디코드로 하고 있다면,
> `/jwt` 에서도 **Base64 디코드**를 골라 만든 토큰을 쓴다.

## 2. 해시 — 문제는 "되돌리기" 가 아니라 "만들기"

해시는 되돌릴 수 없습니다. 맞아요. 근데 그게 문제가 아닙니다.

**해시는 누구나 만들 수 있습니다.** 계산 방법이 공개돼 있으니까요. 이게 문제예요.

### 결제 웹훅으로 보면

결제사가 우리 서버로 이걸 쏩니다.

```
데이터: {"orderId":"A-1","amount":10000}
해시:   4fa5a2b7688809e1d3512426f2602a52dd550c7649cd00b0d05f08ace0421e94
```

서버는 "받은 데이터를 해시해봤더니 같네, 안 깨졌군" 하고 통과시킵니다.

중간에 공격자가 있으면:

```
데이터를 {"orderId":"A-1","amount":10} 으로 바꾸고
해시도  3d529509127be040bce8e96b55da6d88a26587aea3887d43e15f7ac661b450a3 로 다시 계산해서 붙임
```

서버가 해시해보면? **맞습니다.** 통과시켜요. 1만원 결제가 10원이 됩니다.

되돌리기 같은 건 아무도 안 했습니다. 그냥 **공격자도 계산기를 갖고 있어서** 뚫린 거예요.

### 키를 넣으면

```
HMAC(서버만아는키, 원본) = a38518089014112d2e2f7830686866b05e7d8d32f4ada5b86e49e8930c28d88c
```

공격자가 데이터를 바꾸고 다시 계산하려는데 — **키를 모릅니다.** 아무 키나 넣어서 만들면:

```
HMAC(공격자추측, 위조데이터) = fb885a4c82973223b65377fabcda4384d249a1cb6b4eed6e0f4a93cca4e9ae64
```

서버가 진짜 키로 다시 계산한 값과 안 맞습니다. 거부.

### 그래서 키의 역할은

| | 되돌릴 수 있나 | 만들 수 있는 사람 |
|---|---|---|
| **해시** | ❌ | **누구나** |
| **HMAC** | ❌ (똑같이 불가) | **키 아는 사람만** |
| **암호화** | ✅ 키 있으면 | 키 아는 사람만 |

암호화의 키는 **여는 열쇠**입니다. HMAC 의 키는 **만들 자격**이에요. 여는 데는 아무 쓸모 없습니다.

한 줄로:

> **해시** = 이 데이터 안 바뀌었나? (**실수**로 깨진 걸 잡음 — 전송 오류, 파일 손상)
> **HMAC** = 이 데이터 안 바뀌었고, **우리 편이 만든 거 맞나**? (**고의**로 바꾼 걸 잡음)

### 그럼 파일 다운로드 체크섬은 왜 그냥 해시?

우분투 ISO 받을 때 SHA-256 대조하잖아요. 그건 **해시를 다른 경로로 받기** 때문에 됩니다 —
파일은 미러 서버에서, 해시는 공식 사이트 HTTPS 로. 미러가 털려도 해시는 못 바꾸죠.

근데 파일이랑 해시를 **같은 곳에서 같이** 받으면 아무 의미 없습니다.
털린 놈이 둘 다 바꾸면 되니까. 그럴 때 HMAC 이나 전자서명이 필요한 겁니다.

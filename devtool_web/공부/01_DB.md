# 01. DB — 방언 · 타입 · 인덱스 · 트랜잭션 · JPA

> `/dummy`(DB 더미데이터)와 `/convert`(SQL INSERT 출력)를 만들면서 정리한 것.
> 도구를 만들려면 "MySQL 과 PostgreSQL 이 뭐가 다른가"를 **정확히** 알아야 했다. 대충 알면 틀린 SQL 을 뱉는다.
> 기준: MySQL 8.0 · PostgreSQL 16 · Spring Boot 3.x / Hibernate 6

---

## 0. 한 장 요약

| 주제 | 한 줄 |
|---|---|
| 식별자 따옴표 | MySQL `` `col` `` · PostgreSQL·표준 `"col"` · SQL Server `[col]` |
| 문자열 따옴표 | **전부 홑따옴표** `'값'`. 안의 `'` 는 `''` 로 두 번 |
| 돈 | `DECIMAL` 만 쓴다. `FLOAT`/`DOUBLE` 로 돈을 다루면 언젠가 1원이 사라진다 |
| NULL | `NULL = NULL` 은 참이 아니라 **NULL**. 비교는 `IS NULL` |
| 인덱스 | 복합 인덱스는 **앞 컬럼부터** 써야 탄다. 컬럼에 함수를 씌우면 안 탄다 |
| PK | 랜덤 UUID(v4)를 PK 로 쓰면 인덱스가 흩어진다. 쓸 거면 **v7** |
| 트랜잭션 | MySQL 기본 `REPEATABLE READ` · PostgreSQL 기본 `READ COMMITTED` — **다르다** |
| JPA | 기본은 지연 로딩. 목록에서 연관을 건드리면 **N+1** |

## 1. 방언(dialect) — 같은 SQL 이 아니다

`/dummy` 가 DB 종류를 고르게 해 둔 이유다. 단일 출처는 `frontend/src/lib/sqlDialect.js`.

### 1.1 식별자 감싸기

컬럼·테이블 이름이 예약어(`order`, `key`, `user`)이거나 공백·한글을 포함하면 감싸야 한다.

| DB | 감싸기 | 비고 |
|---|---|---|
| MySQL / MariaDB | `` `order` `` | 백틱. `ANSI_QUOTES` 모드를 켜면 `"order"` 도 된다 |
| PostgreSQL | `"order"` | **표준**. 감싸면 대소문자를 그대로 지킨다 |
| SQL Server | `[order]` | `"order"` 도 `QUOTED_IDENTIFIER ON` 이면 가능 |
| Oracle | `"ORDER"` | 감싸지 않으면 **대문자로 접힌다** |
| SQLite | `` `x` `` `"x"` `[x]` 다 받는다 | 관대하다 |

**대소문자 함정** — 여기서 제일 많이 넘어진다.

```sql
-- PostgreSQL
CREATE TABLE Users (userName text);   -- 실제로는 users(username) 으로 접힌다(소문자)
SELECT userName FROM Users;           -- 된다 (양쪽 다 접히니까)
SELECT "userName" FROM "Users";       -- 에러! 그런 이름은 없다

CREATE TABLE "Users" ("userName" text);  -- 이제 진짜 대문자가 섞인 이름
SELECT userName FROM Users;              -- 에러! users 를 찾는데 없다
```

PostgreSQL 은 **감싸지 않으면 소문자로 접고**, Oracle 은 **대문자로 접는다**.
MySQL 은 리눅스에서 테이블명이 대소문자를 가리고 윈도우/맥에서는 안 가린다(파일시스템을 따라간다).

> **실무 결론**: 이름은 전부 소문자 + 언더스코어(`user_name`)로 짓는다.
> 그러면 어느 DB 에서도 따옴표가 필요 없고 이 함정을 통째로 피한다.

### 1.2 문자열 이스케이프

```sql
INSERT INTO t (name) VALUES ('O''Brien');   -- 표준: 홑따옴표를 두 번
```

MySQL 은 백슬래시(`'O\'Brien'`)도 받지만 **표준이 아니다**.
PostgreSQL 은 기본적으로 백슬래시를 문자 그대로 본다(`standard_conforming_strings = on`).
그래서 도구가 SQL 을 만들 때는 **`''` 방식만 쓴다** — 어디서나 동작한다.

이건 그냥 스타일 문제가 아니다. 이스케이프를 문자열 이어붙이기로 처리하면 **SQL 인젝션**이 된다.

```java
// 절대 하지 않는다
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
// name 이  ' OR '1'='1  이면 전부 조회된다

// 파라미터 바인딩 — 값과 코드를 분리한다. DB 가 값을 값으로만 본다
jdbcTemplate.query("SELECT * FROM users WHERE name = ?", rowMapper, name);
```

**JPA/JPQL 도 같다.** `"... WHERE name = '" + name + "'"` 로 만들면 JPQL 인젝션이다.
`:param` 바인딩을 쓴다.

### 1.3 그 밖의 흔한 차이

| 하는 일 | MySQL | PostgreSQL | 표준/기타 |
|---|---|---|---|
| 개수 제한 | `LIMIT 10 OFFSET 20` | 같음 | `OFFSET 20 ROWS FETCH FIRST 10 ROWS ONLY` (표준·Oracle 12c+) |
| 자동 증가 | `AUTO_INCREMENT` | `GENERATED ALWAYS AS IDENTITY` (또는 구식 `serial`) | SQL Server `IDENTITY(1,1)` |
| 문자열 잇기 | `CONCAT(a,b)` (`||` 는 OR 로 해석) | `a || b` | 표준은 `||` |
| 현재 시각 | `NOW()` | `now()` / `CURRENT_TIMESTAMP` | 표준 `CURRENT_TIMESTAMP` |
| 대소문자 무시 검색 | 콜레이션이 `_ci` 면 자동 | `ILIKE` 또는 `lower()` | — |
| Boolean | `TINYINT(1)` (진짜 bool 없음) | `boolean` 진짜로 있음 | — |
| UPSERT | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT ... DO UPDATE` | 표준 `MERGE` |

## 2. 타입 — 잘못 고르면 나중에 못 고친다

### 2.1 숫자

| 타입 | 범위 | 언제 |
|---|---|---|
| `INT` | 약 ±21억 | 보통의 PK·수량 |
| `BIGINT` | 약 ±9.2×10¹⁸ | 회원수가 21억을 넘을 리 없어도 **PK 는 BIGINT 를 권한다** — 삭제/재삽입으로 시퀀스는 실제 행 수보다 훨씬 빨리 는다 |
| `DECIMAL(p,s)` | 정확한 십진수 | **돈·비율·수량** 전부 |
| `FLOAT`/`DOUBLE` | 근사값 | 과학 계산, 좌표. **돈에는 절대 안 쓴다** |

부동소수점이 왜 돈에 안 맞는지는 한 줄이면 보인다.

```java
System.out.println(0.1 + 0.2);              // 0.30000000000000004
System.out.println(new BigDecimal("0.1").add(new BigDecimal("0.2")));  // 0.3
```

이진 부동소수점은 0.1 을 정확히 표현하지 못한다(십진수로 1/3 을 못 적는 것과 같다).
`DECIMAL` 은 십진수를 그대로 저장해서 이 오차가 없다. Java 쪽은 `BigDecimal` 로 받는다.

> `BigDecimal` 비교는 `equals()` 가 아니라 `compareTo()` 로 한다.
> `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` 은 **false** 다 — scale 까지 비교하기 때문이다.

### 2.2 문자열

| 타입 | 성격 |
|---|---|
| `CHAR(n)` | 고정 길이. 짧으면 **공백으로 채운다**. 길이가 진짜 고정인 것(국가코드 `KR`)에만 |
| `VARCHAR(n)` | 가변 길이. 대부분 이걸 쓴다 |
| `TEXT` | 길이 제한 없음. MySQL 에선 인덱스에 제약이 있고(앞 N 바이트만), 정렬 시 임시테이블을 디스크로 내릴 수 있다 |

**MySQL 의 `VARCHAR(n)` 에서 `n` 은 바이트가 아니라 문자 수다**(5.0.3+).
다만 인덱스 크기 한도는 바이트로 걸리므로, `utf8mb4`(문자당 최대 4바이트)에서
`VARCHAR(255)` 를 통째로 인덱싱하면 255×4 = 1020바이트다. 기본 한도(3072바이트)엔 들어가지만
복합 인덱스로 여러 개 묶으면 넘칠 수 있다.

**`utf8` 은 진짜 UTF-8 이 아니다** — MySQL 의 `utf8`(별칭 `utf8mb3`)은 **최대 3바이트**만 저장한다.
이모지(😀, 4바이트)를 넣으면 잘리거나 에러가 난다. **반드시 `utf8mb4`** 를 쓴다.
자세한 건 [02_문자와_인코딩.md](02_문자와_인코딩.md) §2.

### 2.3 시각

[03_날짜와_시간.md](03_날짜와_시간.md) §4 에서 자세히 다루지만 한 줄만:

- MySQL `TIMESTAMP` = UTC 로 저장하고 조회 시 세션 타임존으로 변환. **2038년 문제 있음**
- MySQL `DATETIME` = 적은 값 그대로 저장. 타임존 개념 없음. 범위 넓음
- PostgreSQL `timestamptz` = 권장. `timestamp`(without tz)는 타임존을 안 붙인 벽시계 값

## 3. NULL — 삼치 논리

SQL 의 비교는 참/거짓이 아니라 **참/거짓/알 수 없음(NULL)** 세 가지다.

```sql
SELECT NULL = NULL;      -- NULL (참이 아니다!)
SELECT NULL <> 1;        -- NULL
SELECT NULL IS NULL;     -- true   ← 비교는 이걸로
```

### 걸려 넘어지는 세 곳

**① `NOT IN` 에 NULL 이 섞이면 결과가 통째로 빈다**

```sql
SELECT * FROM users WHERE id NOT IN (1, 2, NULL);   -- 항상 0건!
```

`id NOT IN (1,2,NULL)` = `id<>1 AND id<>2 AND id<>NULL` 인데 마지막이 NULL 이라
전체가 참이 될 수 없다. **`NOT EXISTS` 를 쓰거나 NULL 을 걸러낸다.**

**② 집계 함수는 NULL 을 건너뛴다**

```sql
-- 행이 3개이고 score 가 (10, 20, NULL) 일 때
SELECT COUNT(*),  COUNT(score), AVG(score) FROM t;
--        3           2            15      ← AVG 는 30/2 이지 30/3 이 아니다
```

**③ UNIQUE 제약은 NULL 을 여러 개 허용한다**

대부분의 DB(MySQL·PostgreSQL·Oracle)에서 `UNIQUE` 컬럼에 NULL 은 몇 개든 들어간다.
"NULL 은 서로 같지 않다"고 보기 때문이다. "값이 있으면 유일" 이 필요하면 그대로 두고,
"하나만" 이 필요하면 `NOT NULL` 을 같이 건다.

## 4. 인덱스 — 왜 안 타는가

인덱스는 대부분 **B-tree** 다. 정렬된 상태로 유지되는 트리라 `=`, `<`, `>`, `BETWEEN`,
`LIKE '접두%'`, `ORDER BY` 를 도울 수 있다.

### 4.1 복합 인덱스는 앞에서부터만 쓴다 (leftmost prefix)

```sql
CREATE INDEX idx ON orders (user_id, status, created_at);
```

| 쿼리 조건 | 인덱스 사용 |
|---|---|
| `user_id = 1` | ✅ |
| `user_id = 1 AND status = 'PAID'` | ✅ |
| `user_id = 1 AND status = 'PAID' AND created_at > ?` | ✅ 전부 |
| `status = 'PAID'` | ❌ 앞 컬럼이 빠졌다 |
| `user_id = 1 AND created_at > ?` | ⚠️ `user_id` 까지만. `created_at` 은 못 쓴다 |

전화번호부가 (성, 이름) 순으로 정렬돼 있으면 "김"으로 시작하는 사람은 빨리 찾지만
"이름이 철수인 사람"은 전부 뒤져야 하는 것과 같다.

**범위 조건 다음 컬럼은 못 쓴다** — 위 표의 마지막 줄이 그 이유다.
`>` `<` `BETWEEN` `LIKE '접두%'` 를 만나는 순간 그 뒤 컬럼의 정렬은 깨진다.
그래서 **등호 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에** 둔다.

### 4.2 인덱스를 죽이는 것들

```sql
-- ❌ 컬럼에 함수를 씌우면 인덱스를 못 쓴다
WHERE DATE(created_at) = '2026-08-17'
-- ✅ 컬럼은 그대로 두고 범위로 바꾼다
WHERE created_at >= '2026-08-17' AND created_at < '2026-08-18'

-- ❌ 앞 와일드카드
WHERE name LIKE '%김%'
-- ✅ 접두 검색이면 탄다
WHERE name LIKE '김%'

-- ❌ 타입이 다르면 암묵 변환이 일어나 인덱스를 못 탈 수 있다
WHERE phone = 01012345678      -- phone 이 VARCHAR 인데 숫자로 비교
-- ✅
WHERE phone = '01012345678'
```

`%` 로 시작하는 검색이 정말 필요하면 B-tree 로는 답이 없다 — 전문 검색(FULLTEXT, PostgreSQL `tsvector`)
이나 별도 검색 엔진을 쓴다.

### 4.3 카디널리티 — 인덱스가 항상 이득은 아니다

값의 종류가 적으면(성별, `is_deleted` 같은 boolean) 인덱스를 타도 절반을 읽어야 해서
옵티마이저가 아예 무시하고 풀 스캔을 고른다. **인덱스는 공짜가 아니다** — 쓰기마다 갱신 비용이 들고
디스크를 먹는다. 안 쓰는 인덱스는 지우는 게 낫다.

### 4.4 커버링 인덱스

인덱스만 읽고 테이블에 안 가도 되면 훨씬 빠르다.

```sql
CREATE INDEX idx ON orders (user_id, status, amount);
SELECT amount FROM orders WHERE user_id = 1 AND status = 'PAID';
-- amount 가 인덱스 안에 있으니 테이블 접근이 없다
```

### 4.5 확인하는 법

```sql
EXPLAIN SELECT ...;              -- MySQL: type=ALL 이면 풀스캔, key=NULL 이면 인덱스 못 씀
EXPLAIN ANALYZE SELECT ...;      -- PostgreSQL / MySQL 8.0.18+: 실제로 실행하고 시간까지
```

추측하지 않는다. `EXPLAIN` 이 답을 준다.

## 5. PK 를 무엇으로 할 것인가 — UUID 와 인덱스

`/uuid` 도구가 v1·v3·v4·v5·v7 을 다 만드는 이유가 여기 있다.

| 방식 | 장점 | 단점 |
|---|---|---|
| `BIGINT AUTO_INCREMENT` | 작다(8B) · 순차라 인덱스가 촘촘하다 | 값이 예측된다(URL 에 노출 시 정보) · 여러 DB 를 합칠 때 충돌 |
| **UUID v4** (랜덤) | 어디서 만들어도 안 겹친다 · 예측 불가 | **16바이트** · 완전 랜덤이라 인덱스가 흩어진다 |
| **UUID v7** (시간+랜덤) | v4 의 장점 + **시간순 정렬** | 생성 시각이 값에 드러난다 |

### 왜 랜덤 UUID 가 인덱스에 나쁜가

B-tree 는 정렬을 유지한다. 순차 값(1,2,3…)은 항상 **맨 끝 페이지**에만 추가되니
그 페이지 하나만 메모리에 있으면 된다. 랜덤 값은 **매번 다른 페이지 한가운데**에 꽂히므로,

- 그 페이지를 디스크에서 읽어와야 하고(랜덤 I/O)
- 페이지가 꽉 차 있으면 **쪼갠다**(page split) → 조각화 → 인덱스가 커지고 느려진다

UUID v7 은 앞 48비트가 밀리초 타임스탬프라 **거의 순차**다. 그래서 v4 의 충돌 없음은 유지하면서
인덱스 성능은 auto increment 에 가깝다. RFC 9562(2024)로 표준이 됐다.

> MySQL 에서 UUID 를 저장한다면 `CHAR(36)`(36바이트) 말고
> `BINARY(16)` + `UUID_TO_BIN()` 을 쓴다. 크기가 절반 이하고 비교도 빠르다.
> `UUID_TO_BIN(uuid, 1)` 은 v1 의 시간 필드를 앞으로 재배치해 순차성을 준다(v7 이 없던 시절의 해법).

## 6. 트랜잭션과 격리 수준

**ACID** — 원자성(전부 아니면 전무) · 일관성(제약을 깨지 않음) · 격리성(동시 실행이 서로 안 보임) · 지속성(커밋되면 남음).

### 6.1 동시성에서 생기는 이상 현상

| 현상 | 무슨 일 |
|---|---|
| Dirty Read | 아직 **커밋 안 된** 남의 변경을 읽는다 |
| Non-Repeatable Read | 같은 행을 두 번 읽었는데 **값이 달라졌다**(사이에 남이 UPDATE+커밋) |
| Phantom Read | 같은 조건으로 두 번 조회했는데 **행 수가 달라졌다**(사이에 남이 INSERT) |

### 6.2 격리 수준

| 수준 | Dirty | Non-Repeatable | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| **READ COMMITTED** | 막음 | 발생 | 발생 |
| **REPEATABLE READ** | 막음 | 막음 | 발생(표준상) |
| SERIALIZABLE | 막음 | 막음 | 막음 |

**기본값이 DB 마다 다르다 — 이게 실무에서 진짜 문제다.**

| DB | 기본 |
|---|---|
| MySQL (InnoDB) | `REPEATABLE READ` |
| PostgreSQL | `READ COMMITTED` |
| Oracle | `READ COMMITTED` |
| SQL Server | `READ COMMITTED` |

로컬 MySQL 에서 되던 게 운영 PostgreSQL 에서 다르게 도는 일이 여기서 나온다.

> MySQL 의 `REPEATABLE READ` 는 갭 락(gap lock) 덕분에 팬텀도 대체로 막힌다 — 표준보다 강하다.
> 대신 갭 락은 **데드락의 흔한 원인**이기도 하다.

### 6.3 낙관적 락 vs 비관적 락

```java
// 낙관적 — 충돌이 드물 때. 버전이 안 맞으면 예외
@Entity class Product {
    @Version private Long version;   // UPDATE ... WHERE id=? AND version=?
}

// 비관적 — 충돌이 잦고 재시도 비용이 클 때. 읽을 때부터 행을 잠근다
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Product> findById(Long id);   // SELECT ... FOR UPDATE
```

낙관적 락은 실패 시 **재시도 로직이 반드시 필요하다**. 그게 없으면 사용자에게 에러가 그대로 간다.

## 7. JPA / Hibernate 에서 실제로 터지는 것들

### 7.1 N+1

```java
List<Order> orders = orderRepository.findAll();       // SELECT * FROM orders     ← 1번
for (Order o : orders) {
    System.out.println(o.getUser().getName());        // SELECT * FROM users WHERE id=?  ← N번
}
```

주문 100건이면 쿼리 101번. `@ManyToOne` 의 기본이 `EAGER` 라 오히려 더 조용히 터진다.

**해결 순서**

```java
// 1) fetch join — 가장 직접적
@Query("SELECT o FROM Order o JOIN FETCH o.user")
List<Order> findAllWithUser();

// 2) @EntityGraph — 쿼리를 안 건드리고
@EntityGraph(attributePaths = "user")
List<Order> findAll();

// 3) 컬렉션이 여러 개면 fetch join 을 하나만 하고 나머지는 배치로
// application.yml: spring.jpa.properties.hibernate.default_batch_fetch_size: 100
//   → IN (?, ?, ... ) 로 묶어서 N번을 1~2번으로
```

> **컬렉션 fetch join 은 하나만 가능하다.** 둘 이상이면 카테시안 곱이 나서
> `MultipleBagFetchException` 이 뜬다. 그래서 2번째부터는 `default_batch_fetch_size` 로 푼다.
> 또 컬렉션 fetch join 에는 **페이징이 안 먹는다** — 하이버네이트가 전부 메모리로 가져와 자른다
> (경고 로그 `firstResult/maxResults specified with collection fetch; applying in memory`).

### 7.2 연관관계는 `LAZY` 로 시작한다

```java
@ManyToOne(fetch = FetchType.LAZY)   // 기본이 EAGER 라서 명시해야 한다
private User user;

@OneToMany                            // 기본이 LAZY. 그대로 둔다
private List<OrderItem> items;
```

EAGER 는 "필요 없을 때도 항상 조인" 이라 통제가 안 된다. 전부 LAZY 로 두고
**필요한 곳에서 fetch join 으로 당겨온다**가 원칙이다.

### 7.3 영속성 컨텍스트와 `@Transactional` 경계

트랜잭션 안에서 조회한 엔티티는 **변경 감지(dirty checking)** 대상이다. `save()` 를 안 불러도 커밋 시 UPDATE 가 나간다.

```java
@Transactional
public void rename(Long id, String name) {
    Order o = repo.findById(id).orElseThrow();
    o.setName(name);          // save() 호출 없이도 UPDATE 가 나간다
}
```

반대로 **트랜잭션 밖에서 LAZY 를 건드리면** `LazyInitializationException` 이다.
Spring Boot 는 기본적으로 OSIV(`spring.jpa.open-in-view`)가 **true** 라 컨트롤러까지 세션이 열려 있어
이 예외가 안 나지만, 그건 문제를 감추는 것이다 — DB 커넥션을 응답 끝까지 붙들고 있게 된다.

> **권장**: `spring.jpa.open-in-view: false` 로 끄고, 서비스 계층에서 필요한 걸 다 로딩해
> **DTO 로 변환해서** 내보낸다. 끄는 순간 숨어 있던 N+1 과 지연 로딩이 예외로 드러난다 — 그게 목적이다.

### 7.4 `@Transactional` 이 안 먹는 경우

Spring 의 `@Transactional` 은 **프록시**로 동작한다.

```java
@Service
public class OrderService {
    public void outer() {
        inner();          // ❌ 같은 객체 안에서 부르면 프록시를 안 거쳐 트랜잭션이 안 걸린다
    }
    @Transactional
    public void inner() { ... }
}
```

- **자기 호출(self-invocation)은 안 걸린다**
- `private`·`final` 메서드에는 안 걸린다
- 기본 롤백은 **`RuntimeException` 과 `Error` 에만**. 체크 예외는 롤백 안 한다
  (`@Transactional(rollbackFor = Exception.class)` 로 바꿀 수 있다)

### 7.5 `equals`/`hashCode` 와 엔티티

ID 가 DB 에서 생성되는(`@GeneratedValue`) 엔티티를 `HashSet` 에 넣고 저장하면,
저장 전에는 ID 가 null 이라 해시가 바뀌어 버려 못 찾게 된다.
**비즈니스 키가 있으면 그걸로, 없으면 아예 재정의하지 않는 쪽**이 안전하다.

## 8. 스키마를 바꾸는 법

`ddl-auto: update` 는 **로컬에서만** 쓴다. 운영에서 쓰면 하이버네이트가 판단해서 DDL 을 날리는데,
컬럼 삭제·타입 변경 같은 건 제대로 못 하고 조용히 어긋난다.

```yaml
spring.jpa.hibernate.ddl-auto: validate   # 운영: 엔티티와 실제 스키마가 맞는지 확인만
```

변경은 **Flyway** 나 **Liquibase** 로 버전 관리한다.

```
db/migration/
  V1__init.sql
  V2__add_order_status.sql       ← 한 번 배포된 파일은 절대 수정하지 않는다(체크섬이 깨진다)
  V3__backfill_status.sql
```

**무중단 배포에서 컬럼을 지우려면 두 번에 나눈다.**
① 코드에서 그 컬럼 사용을 없애고 배포 → ② 다음 배포에서 컬럼 DROP.
한 번에 하면 구버전 인스턴스가 없는 컬럼을 찾다 죽는다.

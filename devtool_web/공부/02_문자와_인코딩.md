# 02. 문자와 인코딩 — 유니코드 · UTF-8 · 정규화 · 한글

> `/char-count`(글자수)와 `/unicode` 를 만들면서 정리한 것.
> "글자 수를 센다"는 게 왜 어려운 문제인지 알게 되면, 이 영역의 나머지도 대부분 설명된다.
> 이 문서의 숫자는 전부 실제로 돌려 확인한 값이다.

---

## 0. 한 장 요약

| | 뜻 |
|---|---|
| **코드포인트** | 유니코드가 문자마다 매긴 번호. `한` = U+D55C |
| **인코딩** | 그 번호를 **바이트로 적는 방법**. UTF-8, UTF-16… |
| **코드 유닛** | 인코딩의 최소 단위. UTF-8 은 1바이트, UTF-16 은 2바이트 |
| **자소 묶음(grapheme)** | 사람이 "한 글자"라고 느끼는 덩어리 |

**"글자 수"에 정답이 없는 이유**가 이 표에 다 있다. 무엇을 세느냐에 따라 답이 다르다.

| 문자열 | JS `.length` | 코드포인트 | UTF-8 바이트 | 자소 묶음 |
|---|---|---|---|---|
| `A` | 1 | 1 | 1 | 1 |
| `한` | 1 | 1 | **3** | 1 |
| `😀` | **2** | 1 | 4 | 1 |
| `👍🏽` (피부톤) | **4** | 2 | 8 | **1** |
| `👨‍👩‍👧‍👦` (가족) | **11** | 7 | 25 | **1** |

가족 이모지 하나가 `.length` 로는 **11**이다. 트위터 글자수 제한 같은 걸 `.length` 로 만들면
이모지 하나에 11자를 먹는다.

## 1. 코드포인트와 인코딩은 다른 층이다

유니코드는 **번호만 정한다**. `한` 은 U+D55C 다. 그걸 실제 바이트로 어떻게 적을지는 인코딩의 몫이다.

| 인코딩 | `한` (U+D55C) | 성격 |
|---|---|---|
| UTF-8 | `ED 95 9C` (3바이트) | 가변 1~4바이트. ASCII 와 호환 |
| UTF-16 | `D5 5C` (2바이트) | 가변 2 또는 4바이트 |
| UTF-32 | `00 00 D5 5C` (4바이트) | 고정 4바이트. 거의 안 쓴다 |
| EUC-KR | `C7 D1` (2바이트) | 옛 한국 표준. 유니코드 아님 |

### UTF-8 이 이긴 이유

```
0xxxxxxx                            1바이트  ASCII (U+0000 ~ U+007F)
110xxxxx 10xxxxxx                   2바이트  (~U+07FF)   라틴 확장, 그리스, 키릴
1110xxxx 10xxxxxx 10xxxxxx          3바이트  (~U+FFFF)   **한글·한자·대부분**
11110xxx 10xxxxxx 10xxxxxx 10xxxxxx 4바이트  (~U+10FFFF) **이모지**
```

- **ASCII 가 그대로 ASCII 다** — 영어만 쓰던 기존 시스템·프로토콜이 안 깨진다. 이게 결정적이었다
- **첫 바이트만 보면 길이를 안다** — 중간부터 읽어도 문자 경계를 찾을 수 있다(이어지는 바이트는 항상 `10xxxxxx`)
- 바이트 순서(엔디언) 문제가 없다 → **BOM 이 필요 없다**

> **BOM(`EF BB BF`)은 UTF-8 에서 쓰지 않는다.** 윈도우 메모장이 붙이는 그것 때문에
> CSV 첫 컬럼명이 `﻿id` 가 되어 파싱이 깨지는 일이 흔하다.
> 반대로 **엑셀은 BOM 이 없으면 UTF-8 CSV 를 EUC-KR 로 읽어 한글을 깬다** — 그래서
> "엑셀용 CSV"만 예외적으로 BOM 을 붙인다.

## 2. 저장할 때 — `utf8` 함정

**MySQL 의 `utf8` 은 UTF-8 이 아니다.** 최대 3바이트만 저장하는 반쪽짜리(`utf8mb3`)라
4바이트인 **이모지가 안 들어간다**.

```sql
-- ❌ 이모지를 넣으면 에러 또는 잘림
CREATE TABLE t (msg VARCHAR(100)) CHARACTER SET utf8;

-- ✅
CREATE TABLE t (msg VARCHAR(100)) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

MySQL 8.0 부터 서버 기본이 `utf8mb4` 이지만, 오래된 DB 를 물려받았다면 확인이 필요하다.
**연결 문자셋도 같이 맞춰야 한다** — 테이블만 `utf8mb4` 여도 커넥션이 `utf8` 이면 거기서 깨진다.

### 콜레이션 — 비교·정렬 규칙

| 콜레이션 | 뜻 |
|---|---|
| `utf8mb4_bin` | 바이트 그대로 비교. `A` ≠ `a` |
| `utf8mb4_general_ci` | `ci` = case-insensitive. 빠르지만 부정확한 구석이 있다 |
| `utf8mb4_0900_ai_ci` | MySQL 8 권장. `ai` = accent-insensitive |
| `utf8mb4_unicode_520_ci` | 유니코드 정렬 규칙을 더 잘 따른다 |

`ci` 콜레이션에서는 `WHERE email = 'A@x.com'` 이 `a@x.com` 도 잡는다.
편할 때도 있지만 **비밀번호 해시나 토큰 컬럼에는 `bin`** 을 쓴다 — 대소문자가 뭉개지면 안 된다.

## 3. UTF-16 과 서로게이트 — Java·JS 가 이모지에서 헛도는 이유

Java 의 `char` 와 JavaScript 의 문자열은 **UTF-16 코드 유닛** 배열이다. 2바이트짜리다.
그런데 유니코드는 U+10FFFF 까지 있어서 2바이트에 다 안 들어간다.

그래서 U+FFFF 를 넘는 문자는 **두 개의 코드 유닛(서로게이트 페어)** 으로 표현한다.

```js
"😀".length          // 2      ← 코드 유닛 2개
"😀".codePointAt(0)  // 0x1F600  진짜 코드포인트
"😀".charCodeAt(0)   // 0xD83D   상위 서로게이트
"😀".charCodeAt(1)   // 0xDE00   하위 서로게이트
```

Java 도 똑같다. `"😀".length()` 는 **2**, `codePointCount(0, 2)` 가 1이다.

### 그래서 생기는 사고

```js
"😀".substring(0, 1)   // "\uD83D"  → 반쪽만 잘려서 깨진 문자(�)
[..."😀"].length       // 1   ← 스프레드/for...of 는 코드포인트 단위로 순회한다
```

**문자열을 자를 때 코드 유닛 인덱스로 자르면 이모지가 반토막 난다.**
DB `VARCHAR` 길이 제한에 맞춰 자를 때 실제로 터지는 문제다.

```java
// ❌ 이모지가 반으로 잘릴 수 있다
s.substring(0, 100);

// ✅ 코드포인트 경계를 지킨다
int end = s.offsetByCodePoints(0, Math.min(100, s.codePointCount(0, s.length())));
s.substring(0, end);
```

## 4. 자소 묶음(grapheme) — 사람이 세는 "한 글자"

코드포인트 단위로 세도 아직 부족하다.

```js
"👍🏽".length        // 4
[..."👍🏽"].length   // 2   ← 👍 + 피부톤 수정자
// 사람이 보기엔 1글자
```

피부톤·가족 이모지·국기·결합 문자는 **여러 코드포인트가 하나의 글자로 보인다**.
이걸 제대로 세려면 `Intl.Segmenter` 를 쓴다.

```js
const seg = new Intl.Segmenter("ko", { granularity: "grapheme" });
[...seg.segment("👨‍👩‍👧‍👦")].length;   // 1
```

`/char-count` 도구가 **글자 수·코드포인트·바이트를 따로 보여주는 이유**가 이것이다.
하나로 합칠 수 없다 — 셋 다 맞는 답이고, 쓰임이 다르다.

| 무엇을 셀 때 | 어느 값 |
|---|---|
| 사용자에게 "몇 글자" 보여주기 | **자소 묶음** |
| DB `VARCHAR(n)` 에 들어가는지 | 코드포인트(MySQL 기준 문자 수) |
| 네트워크 전송량, 파일 크기 | **UTF-8 바이트** |
| SMS 요금(한글 SMS 는 70자) | 별도 규칙(UCS-2) |

## 5. 정규화 — "같은 한글인데 안 찾아진다"

같은 글자를 **두 가지 방식으로 표현**할 수 있다.

```js
const a = "한";                 // NFC: U+D55C          — 길이 1
const b = "한".normalize("NFD"); // NFD: U+1112 U+1161 U+11AB — 길이 3 (ㅎ+ㅏ+ㄴ)

a === b                        // false ← 화면엔 똑같이 보이는데!
a === b.normalize("NFC")       // true
```

| 형태 | 뜻 |
|---|---|
| **NFC** | 최대한 **합성**. `한` 한 글자. **웹·DB 의 사실상 표준** |
| **NFD** | 최대한 **분해**. `ㅎ+ㅏ+ㄴ`. **macOS 파일 시스템이 이걸 쓴다** |
| NFKC/NFKD | 호환 문자까지 통일. `①`→`1`, `㈜`→`(주)`. 검색 인덱스에 유용하지만 정보가 손실된다 |

### 실제로 터지는 곳

- **macOS 에서 만든 zip 을 윈도우에서 풀면 한글 파일명이 `ㅎㅏㄴ` 처럼 자소분리** — NFD 로 저장돼서다
- 맥에서 업로드한 파일명을 DB 에 그대로 넣으면 **검색이 안 된다** (NFC 로 친 검색어와 안 맞는다)
- 같은 이유로 `ORDER BY` 결과가 이상해진다

> **원칙: 입력을 받는 경계에서 NFC 로 정규화한다.**
> 파일 업로드, 폼 입력, 외부 API 응답 — 들어오는 지점에서 한 번 통일한다.
> ```java
> Normalizer.normalize(input, Normalizer.Form.NFC)
> ```
> ```js
> input.normalize("NFC")
> ```

## 6. 한글의 구조

### 6.1 완성형 음절 (U+AC00 ~ U+D7A3, 11,172자)

한글 음절은 **계산으로 만들어진다**. 표가 아니라 공식이다.

```
코드포인트 = 0xAC00 + (초성 × 21 × 28) + (중성 × 28) + 종성
```

- 초성 19개 · 중성 21개 · 종성 28개(없음 포함) → 19 × 21 × 28 = **11,172**
- `0xAC00` = `가` (초성 ㄱ, 중성 ㅏ, 종성 없음)
- `0xAC00 + 1` = `각` (종성 ㄱ)

역으로 분해하는 것도 같은 공식이다.

```js
const code = "글".charCodeAt(0) - 0xAC00;
const cho  = Math.floor(code / (21 * 28));   //  0 → ㄱ
const jung = Math.floor((code % (21 * 28)) / 28);
const jong = code % 28;
```

초성 검색("ㄱㅁ" 으로 "김민수" 찾기)이 이 공식으로 만들어진다.

### 6.2 호환 자모 vs 조합용 자모 — 헷갈리는 지점

| 무엇 | 범위 | 예 |
|---|---|---|
| **호환 자모** | U+3131 ~ U+318E | `ㄱ`(U+3131) — 키보드로 치는 자모, 단독으로 보이는 것 |
| **조합용 자모** | U+1100 ~ U+11FF | `ᄀ`(U+1100) — NFD 분해에서 나오는 것 |

**둘은 다른 문자다.** 화면엔 비슷하게 보여도 `"ㄱ" === "ᄀ"` 는 false 다.
NFD 로 분해한 결과와 키보드로 친 자모를 그냥 비교하면 안 맞는 게 이 때문이다.

### 6.3 이 프로젝트의 한글 난수

`/dummy` 의 한글 더미데이터가 처음엔 `뜃뭸퀥냺멛` 같은 글자를 뱉었다.
11,172자에서 **균등하게 뽑으면** 실제로 안 쓰는 조합이 대부분이라서다.
지금은 자주 쓰는 초성 10개 · 중성 8개 · 종성 8개(없음에 가중치)만 조합해 **640가지**로 줄였다.
`lib/dummy.js` 의 `randomHangul()` 이 그 코드다.

## 7. 대소문자 — 생각보다 위험하다

```js
"I".toLowerCase()              // "i"
"I".toLocaleLowerCase("tr")    // "ı"  ← 터키어의 점 없는 i
```

**터키어 문제**로 알려진 것이다. 로케일 기본값으로 대소문자를 바꾸면
터키어 환경의 서버에서 `"ADMIN".toLowerCase() !== "admin"` 이 되어 권한 검사가 뚫린다.

```java
// ❌ 시스템 로케일을 따라간다
s.toLowerCase();
// ✅ 식별자·프로토콜 문자열은 항상 ROOT
s.toLowerCase(Locale.ROOT);
```

독일어 `ß` → 대문자로는 `SS`(길이가 늘어난다), 그리스어 시그마는 위치에 따라 `σ`/`ς` —
**대소문자 변환은 길이가 보존되지 않고 되돌릴 수도 없다.**

`/case` 도구가 케이스 변환을 다루지만, 인증에 쓰는 문자열은 반드시 `Locale.ROOT` 다.

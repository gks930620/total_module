# 10. 다이어그램 (`/erd` `/class-diagram` `/sequence` `/flowchart` `/state-diagram` `/diagram`)

## 무엇을 더하는가 — mermaid.live 가 이미 있는데

mermaid 문법을 배워야 쓸 수 있는 편집기는 이미 여럿 있다. 거기에 하나를 더 얹는 건 의미가 없다.
**이 도구가 더하는 값은 "문법을 배우지 않아도 되는 두 가지"** 다.

| | 넣는 것 | 나오는 것 |
|---|---|---|
| `/erd` | **`CREATE TABLE` 문 그대로** | 테이블·컬럼·PK/FK/UK·관계선까지 그려진 ERD |
| `/class-diagram` | **자바 소스 그대로** | 클래스·상속·구현·JPA 연관이 이어진 UML |

이미 갖고 있는 코드를 붙여넣으면 그림이 나온다. 나머지 네 종류는 문법을 쓰지만,
**한국어 예시**를 넣어 두고 한 줄씩 고치며 익히게 한다.

## 도구 6종

|---|---|---|

| `/sequence` | 시퀀스 다이어그램 | — |
| `/flowchart` | 순서도 | — |
| `/state-diagram` | 상태 다이어그램 | — |

**종류마다 경로를 따로 두는 이유는 검색이다.** "ERD 그리기" 와 "시퀀스 다이어그램" 은 다른 검색어다.
화면이 하는 일은 같으므로 `components/DiagramTool.jsx` 하나를 여섯이 나눠 쓴다.

lib/canvas/geometry.js     도형·간선 기하 — 화면과 내보내기가 같은 그림을 쓰기 위한 공통층

검증할 값이 있는 로직은 전부 순수 함수로 빼 두었다. `mermaidRender.js` 만 DOM 이 필요하고,
거기엔 판단이 없다.

### 모델

파서 둘이 같은 모양을 낸다. 그래야 변환기와 화면이 하나로 끝난다.

```js
{ entities: [{ name, kind, fields: [{name, type, pk, fk, unique, nullable, visibility}], methods }],
  relations: [{ from, to, kind, label, fromCard, toCard }],
  warnings: [] }
```

`kind` — 엔티티는 `table|class|interface|enum|record|abstract`,
관계는 `fk|extends|implements|association|composition`.

> **`lib/dummy.js` 의 `parseSchema` 와 겹쳐 보이지만 다른 물건이다.**
> 저쪽은 **한 테이블**을 더미데이터 생성용으로 읽고(`nullPercent`·`params` 같은 생성 파라미터),
> 이쪽은 **여러 엔티티와 그 사이의 관계**를 읽는다. 관계가 없으면 다이어그램이 아니다.
> 합치려다 양쪽 다 어정쩡해지느니 목적이 다른 파서를 따로 둔다.

## mermaid 를 쓰기로 한 결정

**자체 렌더러를 만들지 않았다.** 레이아웃 엔진(상자 배치·선 라우팅)을 직접 쓰면 mermaid 보다
못한 그림이 나오고, 종류마다 새로 만들어야 한다. 우리가 잘할 수 있는 건 **파싱**이지 배치가 아니다.

### 번들 — 다이어그램을 안 쓰는 사용자를 어떻게 지켰나

mermaid 는 gzip 약 950KB 다. 그대로 넣으면 NFR-04(첫 진입 200KB)를 혼자 다섯 배 넘긴다.
두 겹으로 막는다.

1. **`lib/mermaidRender.js` 밖에서는 mermaid 를 절대 import 하지 않는다** — 동적 `import()` 만 쓴다(pdf-lib 과 같은 방식)
2. **mermaid 가 종류별로 스스로 쪼개진다** — 35개 청크(합계 gzip 262KB)로 갈라져 **쓰는 종류만** 내려온다

실측:

| | gzip |
|---|---|
| 첫 진입 (다이어그램을 안 쓰는 사람) | **74.0KB** — 도입 전과 같다 |
| `/erd` 를 한 번 열 때 추가로 | 약 36KB (화면 11 + 페이지 1 + mermaid 코어 12 + ER 10) |
| 안 쓰는 종류(C4·아키텍처·katex 등) | **받지 않는다** |

### NFR-02 는 그대로다

mermaid 는 순수 클라이언트 렌더러다. 네트워크로 나가지 않는다.
`eval`·`new Function` 을 쓰지 않는 것을 확인했고, CSP `script-src 'self'` 아래에서 그대로 돈다.
`securityLevel: "strict"` 로 사용자 입력의 스크립트·클릭 핸들러를 제거한다.

## 테스트 — 왜 세 겹인가

| 파일 | 무엇을 |
|---|---|
| `diagramParse.test.js` | 코드 → 모델 (27건) |
| `diagramMermaid.test.js` | 모델 → 문법 문자열 모양 (18건) |
| **`diagramMermaidParse.test.js`** | **만든 문법을 mermaid 진짜 파서에 먹여 본다 (26건)** |

세 번째가 핵심이다. **"우리 기준으로 맞다" 와 "저쪽이 받아 준다" 는 다른 문제**다.
문자열 단언은 통과하는데 mermaid 는 거부하는 경우가 실제로 있었다 —

- `classDiagram` 에 주석만 있으면 문법 오류다(`erDiagram` 은 받아 준다)
- `requirement` 이름과 `text:` 값에 한글을 그냥 쓰면 렉서가 죽는다 → 따옴표로 감싸야 한다
- `xychart` 의 축 항목도 마찬가지다
- `id: REQ-1` 의 하이픈이 문법 오류다

전부 **실물 파서에 먹여 보고서야** 나왔다. 화면에 넣어 둔 예시 20종도 이 테스트가 전부 검사한다 —
예시가 깨져 있으면 사용자가 처음 보는 화면이 오류 화면이 된다.

> Node 에는 DOM 이 없어 DOMPurify 가 초기화되지 않는다. 렌더가 아니라 **문법**만 볼 것이므로
> 같은 모듈 인스턴스(ESM 캐시)에 no-op 을 채워 그 단계를 지나가게 했다. `beforeAll` 참조.

## 화면

**넣는 것은 왼쪽, 나온 것은 오른쪽** — 이 프로젝트의 다른 도구와 같다.

- 왼쪽: `/erd` `/class-diagram` 은 **코드 붙여넣기 / 직접 쓰기** 를 고를 수 있다. 나머지는 문법 입력만
- 읽은 뒤에는 **몇 개를 읽었고 몇 개를 이었는지** 숫자로 알리고, 못 읽은 것은 경고로 남긴다 —
  그림에 빠진 게 있는데 모르는 것이 제일 나쁘다
- 오른쪽: 미리보기(확대·축소) · SVG/PNG 저장 · 문법 복사
- 다크 모드에서 mermaid 색이 따라간다(`<html data-theme>` 를 `MutationObserver` 로 지켜본다)
- PNG 는 배경을 칠해서 뽑는다 — 투명 PNG 는 어두운 문서에 붙이면 글자가 안 보인다

## 그리기 탭 — 문법 없이 마우스로

draw.io 를 다 만들지 않는다. 초보 개발자가 프로젝트 문서에 넣을 그림에 필요한 것만:
**상자 놓기 · 드래그로 옮기기 · 점에서 끌어 연결 · 옆 패널에서 내용 고치기 · 실행취소 · 저장.**

- **상태는 문서 객체 하나다**(`lib/canvas/model.js`). 모든 조작이 "문서 → 새 문서" 인 순수 함수라
  실행취소는 이전 문서를 쌓아 두는 것으로 끝나고, 신뢰성 검증이 전부 모델 테스트에 모인다.
- **화면과 내보내기가 같은 기하를 쓴다**(`geometry.js`). 화면은 CSS 토큰으로, 파일은 실색으로
  칠하지만 도형 좌표는 한 곳에서 나온다 — 본 것과 저장된 것이 다르면 편집기를 믿을 수 없다.
- **시퀀스만 편집기가 다르다**. 시퀀스는 좌표가 없고 참가자·메시지의 **순서**가 곧 배치라,
  드래그 캔버스 대신 목록 편집(위아래 이동)이 정확하다.
- `/erd` `/class-diagram` 은 **코드에서 읽은 결과를 '그리기로 보내기'** 로 캔버스에 옮겨
  이어서 편집할 수 있다 — SQL 붙여넣고 배치된 상태에서 시작하는 것이 이 도구의 강점이다.
- 그린 문서는 `dtb.canvas.<종류>` 에 자동 저장(이어서 편집), JSON 으로 내보내기/불러오기,
  SVG·PNG·mermaid 문법으로 내보내기.
- `/diagram`(간트·마인드맵 …)에는 그리기 탭이 없다 — 노드-간선 모델이 아니다.

## 한계 — 파서가 못 읽는 것

완벽한 문법 분석기를 만들지 않았다. 실제로 붙여넣는 건 대개 한 파일 분량의 평범한 코드다.

- 자바 제네릭 메서드·중첩 클래스·애너테이션 안의 복잡한 표현식은 건너뛴다
- SQL 은 `CREATE TABLE`·`ALTER TABLE ... FOREIGN KEY` 만 본다. 뷰·트리거·인덱스는 무시한다
- 못 읽은 것은 **조용히 버리지 않고** `warnings` 로 화면에 띄운다

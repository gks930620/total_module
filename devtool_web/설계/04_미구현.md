# 07. 미구현 도구 — 왜 없고, 만들려면 무엇이 필요한가

> 도구들을 만들면서 **후보로 올렸다가 못 만든 것들**의 기록이다. "안 만들었다" 가 아니라
> **왜 못 만들었는지 · 만들려면 무엇을 포기해야 하는지**를 남겨, 나중에 같은 검토를 반복하지 않게 한다.

---

## 0. 판정 기준 — 이 프로젝트가 못 만드는 것의 정체

거의 모든 미구현 항목은 **한 가지 제약**으로 수렴한다.

> **NFR-02 — 모든 도구가 예외 없이 브라우저 안에서만 동작한다. 서버 API 0개, DB 0개.**

이건 편의상의 선택이 아니라 이 제품의 **유일한 차별점**이다.
"이 사이트는 당신의 파일을 받지 않는다" 를 예외 없이 지킬 때만 의미가 있다.
도구 하나 때문에 서버를 두는 순간 "대부분의 도구는 안전합니다" 가 되고, 그건 경쟁 사이트와 같아진다.

그래서 판정은 이 순서로 한다.

```
① 브라우저 안에서 원리상 가능한가?  → 아니면 A (불가능)
② 가능하다면 비용(번들·성능·정확도)이 감당되는가? → 아니면 B (보류)
③ 외부 데이터·계정·계약이 필요한가? → 그렇다면 C (조건부)
④ 만들 수 있어도 만들면 안 되는가? → 그렇다면 D (의도적 배제)
⑤ 나머지 → E (가능. 다음 후보)
```

| 분류 | 뜻 | 항목 수 |
|---|---|---|
| **A** | 브라우저 원리상 불가능 — 서버·네트워크 권한이 필요 | 8 |
| **B** | 가능하지만 비용이 커서 보류 (번들·성능·정확도) | 7 |
| **C** | 외부 데이터·API 계정·계약이 필요 | 5 |
| **D** | 만들 수 있지만 의도적으로 만들지 않음 | 4 |
| **E** | 제약 없음. 만들면 됨 (다음 작업 후보) | 9 |

## A. 브라우저에서 원리상 불가능 (8)

브라우저의 보안 모델이 막는다. 코드를 잘 짜서 될 문제가 아니다.

### A-1. URL 만 넣으면 OG 태그를 자동으로 읽어오기
- **막는 것** **CORS.** 브라우저 JS 는 다른 출처(origin)의 HTML 을 임의로 읽을 수 없다. `fetch("https://남의사이트")` 는 서버가 `Access-Control-Allow-Origin` 을 내주지 않는 한 차단된다. 그리고 일반 웹사이트는 그걸 내주지 않는다.
- **필요한 것** 서버 프록시 1개 (`GET /api/fetch-meta?url=…`). Spring 에서 대상 URL 을 대신 요청해 HTML 을 파싱하고 OG 태그만 돌려주면 된다. 구현 자체는 반나절이다.
- **딸려오는 대가** 서버 API 가 0개에서 1개가 된다. 그리고 이 API 는 **SSRF 통로**다 — 사용자가 `http://169.254.169.254/`(클라우드 메타데이터)나 내부망 주소를 넣으면 서버가 대신 요청한다. 막으려면 사설 IP 대역 차단·리다이렉트 추적 제한·타임아웃·응답 크기 제한·레이트리밋이 전부 필요하다. 2026-08-04 에 걷어낸 국세청 프록시가 정확히 이 구조였다.
- **지금 한 것** 없다. 값을 직접 붙여넣어 미리보기를 그리던 `/og-preview` 도 걷어냈다.

### A-2. 내 IP 주소 확인
- **막는 것** 브라우저는 자기 공인 IP 를 모른다. 그건 **서버가 요청을 받았을 때만** 알 수 있는 정보다.
- **필요한 것** 서버 엔드포인트 1개(`X-Forwarded-For` 를 읽어 돌려주는) 또는 외부 서비스 호출(ipify 등 — 그러면 사용자 IP 가 제3자에게 넘어간다).
- **판정** 이 제품에서는 **A-1 과 같은 이유로 배제**. "우리는 당신에 대해 아무것도 모른다" 가 핵심 가치인데, IP 를 알아내 보여주는 건 그 반대다.

### A-3. 인터넷 속도 측정 · ping · 포트 스캔
- **막는 것** 속도 측정은 대용량 파일을 내려받을 **서버**가 필요하다. ping(ICMP)·포트 스캔은 브라우저에 소켓 API 자체가 없다.
- **필요한 것** 측정 전용 서버 + 대역폭 비용. 포트 스캔은 브라우저로는 영구히 불가능.
- **판정** 대역폭 비용이 실비로 발생한다. Railway 단일 인스턴스 구성과 맞지 않는다.

### A-4. 도메인 whois · DNS 조회 · SSL 인증서 확인
- **막는 것** whois 는 TCP 43번 포트, DNS 는 UDP 53번. 브라우저에 둘 다 없다. TLS 인증서 체인도 JS 로 열람 불가.
- **필요한 것** 서버 + whois/DNS 클라이언트. DNS-over-HTTPS(Cloudflare `1.1.1.1/dns-query`)를 쓰면 브라우저에서도 DNS 조회는 **가능하다** — 다만 조회 대상이 Cloudflare 에 노출된다.
- **판정** DoH 방식은 기술적으로 열려 있으나 "제3자에게 아무것도 안 보낸다" 원칙과 충돌. 보류.

### A-5. 이메일 주소 실존 확인
- **막는 것** 형식 검증은 정규식으로 되지만(이미 `/regex` 에 있다), **실제로 존재하는 주소인지**는 MX 레코드 조회 + SMTP 대화가 필요하다. 둘 다 브라우저에 없다.
- **필요한 것** 서버 + SMTP 클라이언트. 게다가 요즘 메일 서버 대부분이 이 확인(VRFY)을 막아 놔서 서버를 둬도 정확도가 낮다.
- **판정** 서버를 들여도 결과가 부정확하다. 투자 대비 가치 없음.

### A-6. 단축 URL 만들기
- **막는 것** 단축 URL 은 본질적으로 **"짧은 키 → 원본 URL" 매핑을 어딘가 저장**해야 한다. 저장소 = DB = 서버.
- **필요한 것** DB + 리다이렉트 엔드포인트 + 스팸·피싱 대응(악성 링크 신고 처리, 도메인 평판 관리). 마지막 항목이 실질적으로 가장 무겁다 — 단축 URL 서비스는 피싱에 즉시 악용된다.
- **판정** 서버·DB 0개 원칙과 정면 충돌. **영구 배제.**

### A-7. 파일 공유 · 링크로 결과 전달 · 작업 내용 저장
- **막는 것** 파일을 남에게 전달하려면 중간에 서버가 있어야 한다.
- **필요한 것** 스토리지 + 만료 정책 + 용량 과금 + 불법물 대응.
- **부분 대안** WebRTC 로 **브라우저 ↔ 브라우저 직접 전송**은 가능하다(P2P). 단 연결을 맺어주는 시그널링 서버는 여전히 필요하다(파일 자체는 서버를 안 거친다). 원칙을 절반만 지키는 구조라 별도 판단이 필요하다.
- **판정** 보류. 현재는 localStorage(`dtb.*`)로 **내 브라우저 안에서만** 설정·최근 사용을 기억한다.

### A-8. 실시간 환율 · 주가 · 코인 시세
- **막는 것** 시세는 외부에서 계속 받아와야 하는 데이터다. 대부분의 시세 API 는 CORS 를 허용하지 않는다.
- **필요한 것** API 계정(대개 유료) + 서버 프록시 + 캐시.
- **판정** C 분류(§C-1)와 겹친다. 계정·비용 문제는 사용자 결정 사항.

## B. 가능하지만 비용이 커서 보류 (7)

브라우저에서 **된다.** 다만 대가가 크다. 대부분 "번들 크기" 와 "정확도" 문제다.

### B-1. PPTX / DOCX / XLSX → PDF 변환
- **가능한가** 부분적으로. 오피스 파일은 사실상 **ZIP 안의 XML** 이라 읽는 것 자체는 된다(`jszip` + XML 파싱).
- **문제는 렌더링이다.** PDF 로 바꾸려면 워드/파워포인트의 **레이아웃 엔진을 재현**해야 한다 — 폰트 메트릭, 줄바꿈 규칙, 표 셀 병합, 도형·SmartArt, 애니메이션 무시 규칙, 한글 폰트 임베딩. LibreOffice 가 수십 년째 이 문제를 풀고 있고 여전히 완벽하지 않다.
- **필요한 것 (택1)**
  - ① 서버에 LibreOffice headless 설치 → 원칙 위반 + 인스턴스 메모리 1GB↑ 필요
  - ② `libreoffice-wasm` 같은 WASM 포팅 → **수십~수백 MB** 다운로드. 첫 진입 200KB 예산과 3자리수 차이
  - ③ 자체 렌더러 → 현실적으로 불가
- **판정** 이 도구 하나 때문에 제품 성격이 바뀐다. **만들지 않는다.**
- **대안 안내** 파워포인트·워드의 "PDF 로 저장"(내보내기)이 가장 정확하다. 한글(HWP)은 한컴오피스 자체 기능. 웹에서 굳이 할 이유가 없는 작업이다.

### B-2. PDF → Word / 편집 가능한 문서
- **가능한가** 아니오. **PDF 에는 문단·표 구조가 없다.** "이 좌표에 이 글자" 만 있다. Word 로 되돌리려면 좌표 나열에서 문단·표·읽기 순서를 **역추론**해야 한다.
- **필요한 것** 레이아웃 분석 모델(요즘은 ML 기반). 상용 서비스들도 복잡한 표에서 깨진다.
- **판정** 브라우저 단독으로는 불가. **만들지 않는다.**
- **부분 대안으로 가능한 것** *PDF 에서 텍스트만 추출*은 된다 → §E-1 참조.

### B-3. 이미지 · PDF OCR (글자 인식)
- **가능한가** 된다. `tesseract.js` 가 브라우저에서 동작하고 한국어 학습 데이터도 있다.
- **비용** 엔진 WASM + **한국어 학습 데이터만 10~15MB**. 첫 사용 시 다운로드하고 캐시할 수는 있다(동적 로딩). 인식 시간은 A4 한 장에 수 초~수십 초, CPU 를 크게 먹는다.
- **정확도** 인쇄체 스캔은 쓸 만하고, 손글씨·저해상도·표는 실망스럽다.
- **판정** **기술적으로는 가능. NFR-02 를 지키면서 만들 수 있는 몇 안 되는 무거운 기능이다.** pdf-lib 과 같은 방식(동적 `import()` + "지금 15MB 를 받습니다" 안내)으로 넣을 수 있다. 우선순위상 보류했을 뿐이며 **다음 후보 1순위**다.

### B-4. 동영상 변환 · 압축 · 자르기
- **가능한가** 된다. `ffmpeg.wasm`.
- **비용** 코어 WASM 이 **25~30MB**. 변환 속도는 네이티브 ffmpeg 의 수분의 일. 10분짜리 영상 인코딩에 브라우저 탭이 수십 분 점유되고 메모리가 GB 단위로 오른다. 모바일에서는 대부분 실패한다.
- **판정** 원칙은 지킬 수 있으나 **사용 경험이 나쁜 쪽으로 확실하다.** 보류. 진짜 필요하면 데스크톱 앱(HandBrake)을 쓰는 게 사용자에게 이롭다.

### B-5. 이미지 배경 제거 (누끼)
- **가능한가** 된다. `@imgly/background-removal` 등이 ONNX 모델을 브라우저에서 돌린다.
- **비용** **모델 파일 40~80MB.** WebGPU 가 있으면 빠르고, 없으면 WASM 폴백으로 수십 초.
- **품질** 인물·단순 배경은 쓸 만하고, 머리카락·유리·반투명은 티가 난다.
- **판정** B-3(OCR) 다음 후보. 무게 대비 "와" 하는 효과는 이쪽이 크다.

### B-6. 한국어 맞춤법 · 문법 검사
- **가능한가** 사실상 아니오.
- **왜** 한국어 맞춤법은 **형태소 분석 + 사전 + 규칙**의 조합이다. 부산대 맞춤법 검사기는 서버 기반이고 대량 자동 호출을 금지한다. 클라이언트에 넣으려면 사전·모델을 통째로 내려받아야 하는데 수십 MB 이고, 그렇게 해도 품질은 기존 검사기에 못 미친다.
- **필요한 것** 상용 API 계약(네이버·부산대 등) → 서버 프록시 + 원문이 외부로 전송됨 = **이 제품의 원칙과 정반대**(맞춤법 검사 대상은 대개 자소서·보고서다).
- **판정** **만들지 않는다.** 원칙과 가장 크게 충돌하는 항목이다.
- **부분 대안으로 만든 것** 맞춤법은 아니지만 실무 가치가 있는 것들 — `/char-count`(분량), `/line-fix`(PDF 복사 줄바꿈), `/text`(중복·정렬·번호).

### B-7. 이미지 AI 업스케일 (해상도 향상)
- **가능한가** 된다(Real-ESRGAN 계열 ONNX).
- **비용** 모델 20~60MB + GPU 없으면 한 장에 수십 초.
- **판정** B-5 와 같은 계열. 우선순위 낮음.

## C. 외부 데이터 · API 계정 · 계약이 필요 (5)

**기술 문제가 아니라 계정·비용·계약 문제다. 사용자(프로젝트 소유자)의 결정이 필요하다.**

### C-1. 실시간 환율 · 주가 · 코인 시세
- **필요한 것** 시세 API 계정(한국수출입은행 환율 API 는 무료·키 발급 필요, 그 외 대부분 유료) + CORS 때문에 서버 프록시 + 캐시.
- **정적 대안** 환율은 "고시 환율을 사용자가 직접 입력" 하는 계산기로는 만들 수 있다. 다만 그 정도는 계산기 앱으로도 된다.
- **판정** 서버 도입 여부 = 사용자 결정.

### C-2. 공휴일 · 대체공휴일 반영한 영업일 계산
- **현재** 해당 도구(`/date-calc`)를 걷어내 논의 대상이 없다.
- **필요한 것** 연도별 공휴일 데이터. 공공데이터포털 "특일 정보" API(키 발급 필요) 또는 매년 수동 갱신하는 정적 JSON.
- **정적 JSON 으로 하면** 서버 없이 가능하다(NFR-02 유지). 대신 **매년 사람이 갱신**해야 하고, 임시공휴일이 지정되면 그때도 갱신해야 한다. 갱신을 잊으면 조용히 틀린 답을 준다.
- **판정** **기술적으로는 가능. 유지보수 약속의 문제다.** 넣는다면 데이터 파일에 "언제까지 유효" 를 명시하고 화면에도 표시해야 한다.

### C-3. 주소 검색 · 우편번호 · 지도
- **필요한 것** 도로명주소 API(행정안전부, 무료·신청 필요) 또는 카카오/네이버 지도 SDK(키 필요, 외부 스크립트 로드).
- **판정** 외부 스크립트를 로드하는 순간 그 업체가 방문자를 추적한다. **광고·추적 없음**이라는 약속과 충돌. 배제.

### C-4. 번역
- **필요한 것** 파파고/DeepL API 계정(유료) + 서버 프록시. 원문이 외부로 전송된다.
- **판정** B-6(맞춤법)과 같은 이유로 배제.

### C-5. 계좌 예금주 조회 · 사업자 진위확인
- **현재** 사업자등록번호 진위확인은 **제공하지 않는다**. 계좌·주민번호 형식 검증 도구도 함께 걷어냈다.
- **필요한 것** 금융결제원(계좌) / 국세청(사업자) API — 계약·심사·수수료가 붙는다.
- **제거한 이유** 기술 문제가 아니라 **제품 정체성** 판단이었다(사용자 결정). 개발자 도구 모음에 국세청 API 프록시가 있는 게 어색했고, 그 하나 때문에 서버 API·DB·CORS·레이트리밋·Origin 검증이 전부 딸려 있었다. 제거하면서 **DB 가 통째로 사라졌다.**
- **판정** **되살리지 않는다.** 이 결정은 `01_제품.md` 상단과 `CLAUDE.md` 에도 기록돼 있다.

## D. 만들 수 있지만 의도적으로 만들지 않은 것 (4)

기술 제약이 아니다. **만들면 안 된다고 판단한 것들이다.**

### D-1. 유효한 주민등록번호 생성기
- **가능** 체크섬 규칙을 알면 형식이 유효한 번호를 만드는 건 쉽다.
- **왜 안 만드나** 테스트 데이터라는 명분보다 오남용 위험이 크다. 이미 `/dummy` 코드 주석에 방침으로 못박아 뒀다.
- **대신** `/dummy` 는 이름·주소·전화번호까지만 만든다.

### D-2. JWT 서명 검증
- **가능** WebCrypto 로 HMAC·RSA 검증이 된다.
- **왜 안 만드나** 검증하려면 사용자가 **비밀키/개인키를 웹 페이지에 붙여넣어야** 한다. 우리 사이트가 안전해도(전송 안 함) 그 습관 자체가 위험하다 — 다음번엔 안전하지 않은 사이트에 붙여넣게 된다.
- **대신** `/jwt` 는 해독만 하고 화면에 "서명은 검증하지 않음" 을 명시한다.

### D-3. 브라우저 안 코드 실행기 (JS/Python 플레이그라운드)
- **가능** JS 는 iframe sandbox, Python 은 Pyodide(WASM, ~10MB).
- **왜 안 만드나** ① 이 사이트의 정체성(변환·검증 도구)과 결이 다르다 ② 임의 코드 실행 UI 는 **XSS·피싱 발판**으로 악용되기 쉽다(공격자가 "이 링크 눌러서 이 코드 실행해 봐" 를 우리 도메인으로 할 수 있다) ③ CodePen·Replit 이 이미 훨씬 잘한다.

### D-4. 사용량 분석 · 광고 · 회원가입
- **왜 안 만드나** 제품의 약속 그 자체다 — **광고 없음 · 추적 없음 · 가입 없음.**
- **부수 효과** 그래서 "어떤 도구가 많이 쓰이는지" 를 우리도 모른다. 이건 감수하기로 한 비용이다.

## E. 제약 없음 — 만들면 되는 것 (다음 후보 9)

브라우저에서 되고, 번들도 감당되고, 원칙에도 안 걸린다. **시간 문제로 이번에 못 넣었을 뿐이다.**

| # | 도구 | 어떻게 만들면 되나 | 예상 무게 |
|---|---|---|---|
| E-1 | **PDF 텍스트 추출 · 검색** | `pdf.js`(Mozilla) 로 텍스트 레이어를 뽑는다. 스캔 PDF 는 안 된다(그건 B-3 OCR). | gzip ~90KB, 동적 로딩 |
| E-2 | **ZIP 압축 · 해제** | `jszip`. 한글 파일명 인코딩(CP949) 처리가 실제 난관 — 옛날 압축 파일은 UTF-8 이 아니다. | gzip ~30KB |
| E-3 | **엑셀(XLSX) ↔ CSV/JSON** | `SheetJS`. 이미 만든 `/csv` 에 "엑셀 파일 열기" 를 붙이는 형태가 자연스럽다. | gzip ~150KB, 동적 로딩 |
| E-4 | **SQL 포매터 · 파라미터 바인딩** | 직접 구현 가능. JPA 로그의 `?` 자리에 값을 끼워 실행 가능한 SQL 로 만드는 기능은 실무 가치가 크다. | 0 (자체 구현) |
| E-5 | **Markdown 미리보기 · HTML 변환** | 파서 직접 구현 또는 `marked`. **XSS 살균 필수**(`DOMPurify`). | gzip ~20KB |
| E-6 | **이미지 자르기(크롭) · 워터마크** | Canvas. `/image` 에 이어붙이면 된다. | 0 |
| E-7 | **GIF 만들기 (이미지 → 움직이는 GIF)** | `gif.js`(Web Worker). | gzip ~40KB |
| E-8 | **JSON Path / jq 스타일 질의** | 질의 파서 직접 구현. `/json` 의 검색을 확장하는 형태. | 0 |
| E-9 | **환경변수 ↔ properties ↔ yaml 변환** | 직접 구현. `/convert` 의 확장. `.env` ↔ `application.yml` 은 자주 하는 작업이다. | 0 |

> **E-4 · E-8 · E-9 · E-6 은 외부 의존성이 0** 이다. 다음 작업으로 가장 가볍다.

## 요약 한 장

| 질문 | 답 |
|---|---|
| 왜 오피스 파일 변환이 없나 | 레이아웃 엔진 재현이 필요하다. WASM 포팅은 수십~수백 MB — 제품 성격이 바뀐다 (B-1) |
| 왜 PDF 를 Word 로 못 바꾸나 | PDF 에 문단·표 구조가 애초에 없다. 역추론은 ML 영역 (B-2) |
| 왜 맞춤법 검사가 없나 | 서버·사전이 필요하고, 그러면 자소서 원문이 밖으로 나간다 — 원칙과 정반대 (B-6) |
| 왜 URL 만 넣으면 OG 를 못 읽나 | CORS. 뚫으려면 서버 프록시가 필요하고 그건 SSRF 통로다 (A-1) |
| 왜 내 IP 를 안 보여주나 | 서버만 알 수 있는 정보다. 알아내는 것 자체가 이 제품과 안 맞는다 (A-2) |
| 왜 단축 URL 이 없나 | 저장소=DB=서버. 게다가 피싱 대응 부담이 크다 (A-6) |
| 왜 실시간 환율이 없나 | API 계정·비용·서버 프록시가 필요하다 — 사용자 결정 사항 (C-1) |
| 왜 공휴일 계산이 없나 | 정적 데이터로 가능하지만 **매년 갱신 약속**이 필요하다 (C-2) |
| 그럼 뭘 다음에 만들면 되나 | E 표의 9개. 특히 **E-4 SQL 포매터 · E-1 PDF 텍스트 추출 · B-3 OCR** |

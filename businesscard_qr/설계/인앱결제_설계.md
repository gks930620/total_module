## 1. 무엇을 파는가

| | 무료 | 프로 |
|---|---|---|
| 명함 등록 | **3장까지** | 무제한 |
| 그 외 기능 | 전부 동일 | 전부 동일 |

- 상품 형태: **자동 갱신 구독** 1종. 상품 ID는 **양 스토어 동일**하게 `pro_monthly`.
- 제한은 **등록(create)에만** 건다. 이미 만든 명함은 구독이 끝나도 **조회·수정·삭제 모두 가능**하다.
  (구독 만료로 남의 데이터를 잠그면 스토어 정책·사용자 신뢰 양쪽에서 문제가 된다.)
- 무료 한도는 설정값이다: `app.billing.free-card-limit` (기본 3).

## 2. ERD

```
app_users (기존)
   │ 1
   │
   │ N
subscriptions
```

### `subscriptions`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | BIGINT | PK, AUTO_INCREMENT | 내부 PK (코드컨벤션 §4-1: 기본 Long) |
| `user_id` | VARCHAR(100) | NOT NULL, INDEX | `app_users.id` (예: `kakao_123`) |
| `store` | VARCHAR(20) | NOT NULL | `GOOGLE_PLAY` / `APP_STORE` |
| `product_id` | VARCHAR(100) | NOT NULL | `pro_monthly` |
| `purchase_token` | VARCHAR(512) | NOT NULL, **UNIQUE(store, purchase_token)** | Google=purchaseToken, Apple=originalTransactionId |
| `status` | VARCHAR(20) | NOT NULL | `ACTIVE` / `EXPIRED` / `CANCELED` / `PENDING` / `REVOKED` |
| `expires_at` | DATETIME | NULL 허용 | 구독 만료 시각. 스토어가 준 UTC 값을 **서버 시간대의 `LocalDateTime`** 으로 변환해 저장한다 — 앱 전체가 `LocalDateTime.now()` 로 비교하므로 기준을 맞춘다 |
| `auto_renewing` | BOOLEAN | NOT NULL | 다음 주기에 자동 갱신되는지 |
| `created_at` / `updated_at` | DATETIME | NOT NULL | |

**`UNIQUE(store, purchase_token)` 가 이 설계의 핵심 안전장치다.**
같은 영수증을 여러 계정에 붙여 프로를 무한 복제하는 것을 DB 레벨에서 막는다.
이미 다른 사용자에게 묶인 토큰으로 검증을 시도하면 **409 Conflict** 로 거부한다.

**프로 판정**: `status = ACTIVE` 이고 `expires_at > now()` 인 구독이 하나라도 있으면 프로.

## 3. API 계약

모든 응답은 기존 공통 포맷 `{ success, message, data }` 를 따른다.
두 엔드포인트 모두 **인증 필요**(Bearer JWT). 사용자 식별은 **토큰 주체에서만** 꺼낸다 — 클라이언트가 보낸 userId 를 믿지 않는다(코드컨벤션 §4-1).

### 3-1. `GET /api/billing/entitlement`

지금 이 사용자가 프로인지, 명함을 몇 장 더 만들 수 있는지.

```json
{
  "success": true,
  "message": "Entitlement loaded",
  "data": {
    "pro": false,
    "store": null,
    "product_id": null,
    "expires_at": null,
    "card_count": 2,
    "card_limit": 3
  }
}
```

- `card_limit` 이 **`null` 이면 무제한**(프로). 숫자면 그 수까지만 만들 수 있다.
- `pro: true` 면 `store` / `product_id` / `expires_at` 이 채워진다.

### 3-2. `POST /api/billing/purchases/verify`

앱이 스토어 결제를 마친 뒤 **영수증을 서버에 보내 검증**받는다.
**클라이언트 말을 믿고 권한을 주지 않는다** — 서버가 직접 스토어 API 에 물어본다.

요청:
```json
{
  "store": "GOOGLE_PLAY",
  "productId": "pro_monthly",
  "purchaseToken": "<Google purchaseToken 또는 Apple originalTransactionId>"
}
```

응답: `GET /api/billing/entitlement` 와 **같은 형태**(검증 후 최신 상태).

에러:

| 상황 | 상태 | 설명 |
|---|---|---|
| 모르는 상품 ID | 400 | `app.billing.pro-product-ids` 에 없는 값 |
| 스토어가 "구매 없음/무효" 판정 | 400 | 위조·취소·환불된 영수증 |
| 이미 **다른 사용자**에게 묶인 영수증 | 409 | 계정 간 영수증 돌려쓰기 차단 |
| 스토어 자격증명 미설정 / 스토어 응답 실패 | 503 | 우리 설정 문제이거나 스토어 장애 — 앱은 재시도 안내 |

### 3-3. 명함 등록 한도 위반

`POST /api/business-cards` 에서 무료 사용자가 한도를 넘기면:

```json
{ "success": false, "message": "...", "errorCode": "CARD_LIMIT_EXCEEDED" }
```
상태 **400**. 앱은 이 `errorCode` 를 보고 결제 화면을 띄운다(문구는 앱이 번역).

## 4. 스토어 검증 방식

### 4-1. Google Play
1. 서비스 계정 JSON 의 `private_key` 로 **RS256 JWT** 를 만들어 `https://oauth2.googleapis.com/token` 에서 access token 을 받는다 (scope `androidpublisher`).
2. `GET androidpublisher/v3/applications/{packageName}/purchases/subscriptionsv2/tokens/{token}`
3. `subscriptionState` 로 상태를, `lineItems[].expiryTime` 으로 만료를 읽는다.
4. `acknowledgementState` 가 미승인이면 **승인(acknowledge)** 한다.
   ⚠️ 승인하지 않으면 Google 이 **3일 뒤 자동 환불**한다.

필요한 환경변수: `APP_BILLING_GOOGLE_SERVICE_ACCOUNT_JSON`, `APP_BILLING_ANDROID_PACKAGE_NAME`

### 4-2. Apple App Store
1. App Store Connect API 키(.p8)로 **ES256 JWT** 를 만든다.
2. `GET https://api.storekit.itunes.apple.com/inApps/v1/subscriptions/{originalTransactionId}`
3. 응답의 서명된 거래정보(JWS)에서 payload 를 읽어 만료·상태를 확인한다.

> JWS 서명 체인까지 검증하지 않는 이유: 이 값은 **우리가 Apple 서버에 직접 물어봐 TLS 로 받은 응답**이고,
> 그 호출 자체가 우리 API 키로 인증된다. 서명 체인 검증이 꼭 필요한 건 클라이언트가 건네준 영수증이나
> App Store Server Notifications 처럼 **출처를 신뢰할 수 없는 경로**다.

필요한 환경변수: `APP_BILLING_APPLE_ISSUER_ID`, `APP_BILLING_APPLE_KEY_ID`, `APP_BILLING_APPLE_PRIVATE_KEY`, `APP_BILLING_APPLE_BUNDLE_ID`

### 4-3. 자격증명이 없을 때 (로컬 개발)
- 검증기는 **꺼진 상태**가 되고 `/verify` 는 **503** 을 돌려준다.
- **절대 자동 승인하지 않는다.** "설정 없으면 통과"는 그대로 운영에 나가면 결제 우회 구멍이 된다.
- 부팅을 막지는 않는다(fail-fast 아님) — 결제를 안 쓰는 기존 배포가 그대로 떠야 하기 때문. 대신 시작 시 경고 로그를 남긴다.

## 4-4. 방어 장치 정리 (보안 검토 2026-08-26)

| 위협 | 막는 방법 | 위치 |
|---|---|---|
| 위조 영수증으로 프로 획득 | 서버가 스토어에 직접 조회. 클라이언트 말은 근거로 쓰지 않는다 | `BillingService` |
| 같은 영수증을 여러 계정에 붙이기 | `UNIQUE(store, purchase_token)` + 저장 직전 소유자 재확인 | DB + `SubscriptionRegistrar` |
| 남의 userId 로 구독 붙이기 | 요청 본문에서 userId 를 **아예 받지 않는다**. JWT 주체만 사용 | `PurchaseVerifyRequest` |
| **영수증 값으로 스토어 API 경로 조작** | 형식 검증(`^[A-Za-z0-9._~-]{1,512}$`) + URI 템플릿 변수로 전달(인코딩) | `PurchaseVerifyRequest`, 두 검증 클라이언트 |
| **스토어 무응답으로 스레드 고갈** | 연결 5초 / 읽기 10초 타임아웃 | `BillingHttpConfig` |
| 로그로 영수증 유출 | 스토어 응답 본문을 로그에 남기지 않는다(상태코드·예외 타입만) | 두 검증 클라이언트 |
| 자격증명 미설정 시 우회 | 통과가 아니라 **503** | `RoutingStoreReceiptVerifier` |

## 5. 아직 안 한 것 (다음 과제)

### 5-1. 검토에서 확인했지만 지금은 두기로 한 것

- **`/verify` 요청 빈도 제한 없음** — 형식이 맞는 값이면 매번 스토어를 호출한다.
  악용해도 우리 데이터가 새지는 않지만 외부 API 호출이 늘어난다.
  지금은 형식 검증이 쓰레기 값을 대부분 걸러 주고 트래픽 자체가 거의 없어 두었다.
  사용자가 늘면 사용자별 분당 호출 상한을 붙인다.

- **명함 한도 동시성(TOCTOU)** — `assertWithinCardLimit` 이 센 뒤 저장하기까지 사이에
  같은 사용자가 요청을 여러 개 동시에 보내면 한도를 조금 넘길 수 있다(2장 남았을 때 3개 동시 등록 등).
  막으려면 사용자 행 비관적 락이 필요한데, 명함 생성은 **버킷 업로드 때문에 일부러 트랜잭션 밖**에 두었다
  (코드컨벤션 §1). 이득(무료 몇 장)보다 비용이 커서 두었다. 한도가 매출에 직결되면 그때 다시 본다.

- **RTDN / App Store Server Notifications** — 갱신·취소·환불을 스토어가 먼저 알려주는 웹훅.
  지금은 앱이 켜질 때 `/entitlement` 를 조회하고, 만료 시각이 지나면 프로가 풀리는 **만료시각 기반**이다.
  환불 즉시 회수까지 필요해지면 웹훅을 붙인다.
- **구독 상태 주기적 재조회 배치** — 위와 같은 이유로 아직 없다.
- **가격·구독 기간**은 스토어 콘솔에서 정한다. 서버는 상품 ID 만 안다.
